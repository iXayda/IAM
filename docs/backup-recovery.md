# 备份与恢复

数据库归档含身份资料、密码摘要及加密秘密，按凭据存储等级保护。恢复由授权维护人员执行，组织独立保存批准记录和审计证据。

## 备份材料

- 完整 PostgreSQL custom 格式数据库归档。
- 与快照匹配的签名、TOTP 和授权状态保护文件版本；TLS 与部署配置的可信恢复来源。
- 构建、迁移及 PostgreSQL 主版本、issuer、备份起止时间、归档 SHA-256 和秘密保管系统版本标识。
- 独立授权与审计证据，用于核对快照之后的人员、凭据和应用变化及审计缺口。

保护文件由独立秘密保管系统保存，不放入数据库归档或普通日志。备份期间冻结保护文件与签名密钥变更，协调数据库快照与文件版本；数据库快照不能替代外部材料备份。

使用官方 PostgreSQL 工具及预先配置的 `PGHOST`、`PGPORT`、`PGDATABASE`、`PGUSER`，密码通过受保护的连接配置或 `0600` 权限密码文件提供：

```bash
umask 077
export IAM_ARCHIVE=/secure/backup/iam.dump
pg_dump --format=custom --file="$IAM_ARCHIVE"
sha256sum "$IAM_ARCHIVE"
pg_restore --list "$IAM_ARCHIVE"
```

将校验值保存到独立受控记录；归档旁的可改写摘要不能单独证明来源。加密、异地保管和保留周期由组织确定，定期实际演练恢复，不能仅以能列出归档内容认定成功。

## 离线还原

1. 停止 IAM 及全部使用该库的进程，关闭业务入口，保留事故现场和独立审计证据。
2. 核实授权、归档来源和独立记录的摘要，在隔离环境建立由维护账号拥有的全新空库。
3. 使用与备份相同 PostgreSQL 主版本的工具，还原到核实后的目标，不覆盖在线库：

```bash
export IAM_RESTORE_DATABASE=iam_restore
pg_restore --dbname="$IAM_RESTORE_DATABASE" --single-transaction --exit-on-error \
  --no-owner --no-privileges "$IAM_ARCHIVE"
```

`--no-owner` 保持维护账号拥有对象，`--no-privileges` 不还原旧运行授权，单事务避免部分还原；此处不并行恢复。随后将 JDBC 所有者连接指向同一目标，使用同版本 JAR 执行 `migrate`，保持 Web 停止。

## 隔离旧安全状态

保持唯一维护连接，在受控交互终端执行：

```bash
java -jar target/iam.jar quarantine-restore
```

输入操作人、授权单号、独立记录的 SHA-256 和本地归档路径，以 `QUARANTINE:<数据库名>` 确认。命令重新计算摘要，校验数据库所有者及无其他客户端，关闭自动迁移并限制单个维护连接。它不接受附加参数或管道输入。

摘要与数据库名不能自行证明归档和目标库的对应关系，操作人必须核实实际还原过程。隔离前禁止 Web 访问，不能依赖旧数据库内的标识发现所有快照回滚。

| 对象 | 隔离结果 |
| --- | --- |
| 身份与管理资格 | 保留身份 UUID 和资料，禁用全部用户，清除密码、因素、恢复码和旧管理员资格，永久关闭初始化 |
| 会话与证明 | 清空旧 IAM 会话、授权、刷新家族与历史、交互及单次开通和恢复凭据 |
| 应用权限 | 禁用资源、角色及客户端，清除角色绑定和允许角色，废止旧客户端与资源校验秘密 |
| 签名 | 历史密钥标记失陷并清除私钥，保留公钥及不可重置的初始化与失陷标记 |
| 审计 | 保留原记录，新增归档与快照证据，明确记录 `unresolved` 审计缺口 |

隔离不要求解密旧秘密。安全状态与成功审计原子提交，失败时整笔回滚。相同归档在同一有效隔离状态下重复执行返回原记录；条件不再满足时拒绝。

隔离后保持停服，Web 在监听前拒绝启动。禁止重新执行 `bootstrap-admin`、手工清空隔离标记或直接恢复旧密码绕过核验。终端输出失败时先凭关联 UUID 核查审计，不盲目重复。

## 重新建立管理员入口

保持停服，依据当前权威人员记录核验一个既有用户 UUID，由另一名授权人员独立批准。不能仅依据快照中的管理员名单或请求中临时提供的联系方式。

配置目标库所有者连接和可信 TOTP 保护文件，安排本人使用受控终端：

```bash
java -jar target/iam.jar recover-restored-admin
```

核对独立事故记录中的隔离 UUID、用户 UUID 和数据库，以 `RECOVER:<数据库>:<隔离UUID>:<用户UUID>` 确认。本人设置新密码、绑定并验证新认证器，随后因素、一个新管理员资格、新恢复码及成功审计原子提交。

准备阶段不授予管理权限。中断或过期后，经重新核验授权可对同一身份再次准备，前次待验证密码和因素失效；不能切换已保留身份，完成后不能重复恢复。身份选错时保持隔离，重新走受控还原，不修改不可变记录。

通过预登记可信渠道通知本人，记录关联 UUID 和交付结果，不录屏或采集秘密。已提交但恢复码展示失败时先查审计，不重复恢复。此步骤不解除隔离，其他账号和应用仍禁用，初始化永久关闭，审计缺口仍为 `unresolved`。

## 核验并解除隔离

1. 保持停服，用可信签名保护文件执行 `recover-signing-key`，生成本次隔离之后的新签名身份；从未初始化签名的快照使用 `initialize-signing-key`，不恢复旧私钥。配置可信 TOTP 和独立授权状态保护文件。
2. 独立复核人员、凭据交付、归档与数据库对应关系、issuer、TLS 及代理配置。接入应用清除旧本地会话、Token 和密钥缓存；记录在线缓存及纯离线最长 330 秒撤销窗口的影响，不能由数据库记录代替外部执行证据。
3. 获得独立放行批准后，安排新管理员在受控终端执行：

```bash
java -jar target/iam.jar release-restore
```

填写操作人、放行单号、隔离 UUID、新管理员 UUID 和新密钥 UUID，以 `RELEASE:<数据库>:<隔离UUID>:<管理员UUID>:<新密钥UUID>` 确认，并验证新密码与未消费动态码。绑定因素时已用的动态码不能重放，必要时等待下一真实时间步。

命令校验唯一维护连接、新管理员、新因素、新签名及授权保护配置，并确认其他主体仍禁用、旧会话及授权已清空。放行、因素消费和成功审计原子提交，失败保持隔离。记录不可变恢复证据，不删除原隔离标记或抹平审计缺口；重复放行拒绝。

4. 重新应用 [运行授权清单](../deploy/postgresql/grant-runtime.sql)，以受限账号启动，验证就绪、新管理员登录及 MFA 后受控开放入口。其他用户、客户端秘密、精确回调、资源和角色绑定按当前授权记录逐项重建，不批量恢复快照权限。

再次还原任意新归档时，重复完整停服和隔离流程，建立新的隔离记录并重新废止旧安全状态；归档中已有放行记录不能证明本次还原安全。保留期、RPO / RTO 和实际人员、通知渠道由组织确定，通过演练记录验证。
