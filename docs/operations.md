# 运维指南

## 维护前提

维护命令使用与数据库及 Web 服务版本一致的 JAR，从部署环境读取连接和保护文件配置。命令独立运行，不监听 HTTP。交互命令要求真实控制台，不接受附加参数或管道输入；密码和动态码使用无回显输入。

使用专用数据库，维护账号执行迁移和离线命令，Web 使用受限运行账号。连接配置分别注入，Web 进程不持有维护密码。首次安装的角色、连接及启动配置见 [README](../README.md#开发与运行)。

容器中的三类保护文件位于 `/run/iam`，允许 UID `10001` 读取；IAM 提供 HTTPS 时，还需在此提供 TLS 密钥库。镜像与维护 JAR 保持同一版本。构建和镜像选择见 [容器运行](../README.md#容器运行)及 [.env.example](../.env.example)，运行镜像不包含组织秘密。

## 持久保护文件

| 环境变量 | 内容 |
| --- | --- |
| `IAM_TOTP_KEY_FILE` | TOTP 保护文件，32 个原始二进制字节 |
| `IAM_SIGNING_KEY_FILE` | 签名私钥保护文件，32 个原始二进制字节 |
| `IAM_AUTHORIZATION_KEY_FILE` | 协议授权状态保护文件，64 个原始二进制字节 |

三种文件相互独立，不能替换。限制为部署服务及授权维护人员读取，与对应数据库版本协同备份；重启不应重新生成。签名保护文件缺失、不匹配或签名材料损坏会阻止 Web 启动。材料故障时先核实配置和备份来源，不能通过清空签名表或临时新建保护文件恢复服务。

## 数据库安装与升级

配置数据库所有者连接及持久签名保护文件，执行安装命令：

```bash
java -jar target/iam.jar migrate
java -jar target/iam.jar initialize-signing-key
```

重复初始化签名身份只验证并加载原身份，不生成替代密钥。管理员初始化和恢复不会隐式初始化签名密钥。

使用所有者的 `psql` 连接应用 [运行授权清单](../deploy/postgresql/grant-runtime.sql)。以下命令采用已配置的 `PGHOST`、`PGPORT`、`PGDATABASE` 和 `PGUSER`，密码通过受保护的密码文件或部署秘密管理提供：

```bash
psql -X --set=runtime_role=iam_runtime --set=iam_schema=public --file=deploy/postgresql/grant-runtime.sql
```

清单以事务方式清除旧授权并显式授予业务所需权限。运行账号不能建表、执行迁移、删改审计记录、变更管理员资格或签名密钥；不能拥有数据库对象、加入其他角色或取得提权能力。`runtime` profile 关闭启动迁移并校验受限身份，新增表不自动授权。

默认使用 `public` schema。自定义 schema 时，先由所有者创建，并将 JDBC 的 `spring.datasource.hikari.schema`、Flyway 的 `spring.flyway.schemas` / `spring.flyway.default-schema` 和脚本的 `iam_schema` 配成同一值。

升级前备份数据库与匹配保护文件，停止服务，以所有者迁移并重新应用运行授权清单，再以受限账号启动和验证就绪。

## 初始化管理员

开始前完成数据库迁移，配置数据库所有者连接和持久 TOTP 保护文件。

由组织授权人员核验管理员身份，安排本人在受控终端执行：

```bash
java -jar target/iam.jar bootstrap-admin
```

按提示创建账号或选择活动账号，验证密码，绑定并验证新认证器，安全保存一次性展示的恢复码。初始化只允许完成一次，中断后可继续，完成后不能重复获取资格或恢复码。

终端不得录屏或采集秘密输出。系统成功审计证明技术事务已提交，不能证明操作者已经核验本人或凭据已送达。

## 人工核验与开通交付

组织指定管理员核对当前权威人员记录，确认不可变用户 UUID、业务归属和申请依据。高权限开通由另一名授权人员独立复核；不能仅凭用户名、能够登录的会话或本次请求新提供的联系方式认定本人。

管理员签发一次性开通凭据，交付给本人自行设置密码。使用事先登记并独立核验的组织渠道；凭据与核验记录分开保存，不进入工单正文、源码、聊天群或普通日志。组织应选定实际渠道及负责人，不由 IAM 推测可用邮箱或电话号码。

原申请记录关联核验人、依据类型、批准人、用户 UUID、操作关联 UUID、交付时间及结果，不附身份证明副本、密码或单次凭据。交付失败时先核查提交状态，再取消或重新签发；通知失败不通过回退已提交事务处理。

## 密码恢复交付

密码恢复重新执行本人核验和授权，不将持有旧会话当作充分依据。一次性恢复凭据与开通凭据用途隔离，按相同的预登记可信渠道交付；不得用管理员指定的临时密码替代本人设置。

## 管理员丢失因素

当前密码仍可用但认证器和全部恢复码丢失时，先核验既有活动管理员的 UUID，取得独立批准并停止服务。恢复前指定通知责任人及事先核验的独立渠道。配置数据库连接和可信 TOTP 保护文件，由本人执行：

```bash
java -jar target/iam.jar recover-admin
```

按提示填写操作人、授权单号和用户 UUID，验证当前密码并完成新因素验证。完成前保留原因素；完成后旧恢复码和 IAM 会话失效，原密码与管理员资格保留。初始化不会重新开放，也不会自动登录。

确认提交后，通过该渠道通知本人，在原授权记录中记录关联 UUID、通知时间、执行人和交付结果。若报告已提交但恢复码展示失败，核查审计，用新因素登录后重新生成恢复码，不盲目重复恢复。

通知不含秘密，失败时记录、重试并升级安全负责人，不通过回退恢复或重复运行命令处理通知故障。

## 管理员同时丢失密码与因素

保持停服，按当前权威记录核验既有管理员 UUID，并取得第二人独立批准。不能由快照中的旧资格或请求方新提供的联系方式自行批准恢复。

```bash
java -jar target/iam.jar recover-admin-credentials
```

按提示输入 `RECOVER`，填写操作人、授权单号和管理员 UUID，录入展示的新 TOTP 秘密，设置与旧密码不同的新密码并验证新动态码。准备阶段不替换旧凭据；证明有效期为 10 分钟，并绑定当前操作人、授权记录及原凭据版本。

完成时密码、因素、旧恢复码、恢复证明和 IAM 会话一并更新或失效，并交付新恢复码。新因素验证前退出不代表恢复完成。发生输出失败时先凭关联 UUID 核查审计，按已提交状态处理交付，不能假定回滚或重放已消费证明。

## 安全变更与应用授权

密码、因素及账号安全状态变更还会撤销相应应用授权。恢复人员应通知接入应用处理旧 Token 与本地会话，不能把 IAM 凭据恢复等同于应用已经退出。

## 签名密钥轮换

授权维护人员使用原签名保护文件执行：

```bash
java -jar target/iam.jar rotate-signing-key
```

按提示填写操作人、授权单号并确认当前密钥 UUID。轮换与审计原子提交，清除旧私钥，旧公钥保留 330 秒；此后签发和刷新使用新密钥。报告已提交但输出失败时先核查关联审计，不重复轮换。

## 签名密钥疑似失陷

先停止 IAM 并隔离事件，配置授权状态保护文件后执行 `compromise-signing-key`，确认受影响密钥。该密钥从公钥和在线验证中移除，使用过该密钥的授权及刷新家族撤销；当前密钥失陷会暂停签发。

业务应用独立清理密钥和在线校验缓存，结束受影响本地会话。完成处置后，用可信签名保护文件执行 `recover-signing-key`，确认暂停签发的失陷密钥，生成新签名身份。旧密钥和已撤销授权不会恢复。

两个命令均使用本指南的 `java -jar` 入口及受控交互终端。保护文件本身也失陷时，先按事件范围隔离受影响历史材料并更换文件，不仅处理当前密钥。

## 清理过期协议状态

用数据库所有者连接操作已迁移的数据库，先预览再清理：

```bash
java -jar target/iam.jar preview-protocol-cleanup
java -jar target/iam.jar cleanup-protocol-state
```

两个命令固定关闭自动迁移，不删除安全审计。只清理越过授权码、Token、刷新家族的最后有效时间及额外 330 秒保留窗口的授权，以及已过期交互；父 Refresh Token 已消费不代表家族可删除。

| 配置属性 | 默认值 | 范围 |
| --- | --- | --- |
| `iam.protocol-cleanup.batch-size` | 100 | 1–100 |
| `iam.protocol-cleanup.maximum` | 1000 | 批大小至 10000 |
| `iam.protocol-cleanup.seconds` | 30 | 1–300 秒 |

需要调整时通过 JVM 系统属性在 `-jar` 前传入，例如 `java -Diam.protocol-cleanup.maximum=200 -jar target/iam.jar preview-protocol-cleanup`。

预览对授权和交互分别限额，不代表全库总数。清理对两类合计限额，跳过繁忙授权，各批独立提交；某批失败回滚该批，之前已提交批次保留。检查结果后可按维护计划再次运行，不通过直接删表绕开重放保护。

## 健康检查与故障定位

主 HTTPS 端口的 `GET /livez` 检查进程，`GET /readyz` 检查数据库、必要审计、授权保护配置与签发材料；不可用返回 503。对应 Actuator 分组路径为 `/actuator/health/liveness` 和 `/actuator/health/readiness`，其余管理端点不开放。探针只返回总体状态，不建立会话、写入审计或消耗浏览器登录入口的限流预算。

| 现象 | 处理 |
| --- | --- |
| issuer 校验失败 | 检查显式 HTTPS issuer 的格式和所用配置，不按请求 Host 推导 |
| 签名或保护材料加载失败 | 核对数据库与文件版本，不清空记录或重新生成文件掩盖问题 |
| 数据库权限拒绝启动 | 核对运行身份、schema 及同版本授权清单，不扩大到所有者权限 |
| 就绪失败而存活正常 | 撤出流量，按内部日志定位数据库、审计或签发能力，修复后再验证 |

监控使用可信 CA 验证 HTTPS，在网络入口限制探针调用来源。数据库故障和签名失陷应撤出业务流量，不应依靠存活探针重启解决。

已知审计写入故障在本实例中保留，真实审计成功提交后解除；无法送入正常请求时，修复存储后按受控重启流程重新验证。内部诊断仍须脱敏，不将秘密材料写入普通日志。

## 备份恢复入口

旧数据库归档必须经过 [离线还原与隔离](backup-recovery.md)，不能直接接回 Web。备份保留期、RPO / RTO、维护审批人及真实通知渠道由组织确定，并通过恢复演练核实。
